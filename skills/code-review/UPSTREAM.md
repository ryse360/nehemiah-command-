## Port: `gh` CLI -> GitHub MCP tools

Upstream drives GitHub through the `gh` CLI. `gh` is not installed in Claude
Code web sessions; GitHub access there is through the MCP server's
`mcp__github__*` tools. Run unmodified, the command fails at step 3 (fetching
the PR) and again at step 8 (posting the comment).

Changes made, all mechanical:

| Upstream | Ported |
|---|---|
| `allowed-tools: Bash(gh issue view:*), Bash(gh search:*), Bash(gh issue list:*), Bash(gh pr comment:*), Bash(gh pr diff:*), Bash(gh pr view:*), Bash(gh pr list:*)` | `Task`, five `mcp__github__*` tools, `Read`/`Glob`/`Grep`, and read-only `Bash(git …)` for local blame |
| `gh pr view` (state, draft, prior review) | `pull_request_read` with `method: "get"` and `method: "get_comments"` |
| `gh pr diff` | `pull_request_read` with `method: "get_diff"`, falling back to `get_files` with pagination on large diffs |
| `gh pr list` / `gh search` for prior PRs touching a file | `list_commits` with `path`, then `search_pull_requests` to map commits back to PRs, then `pull_request_read` for their comments |
| `gh pr comment` | `add_issue_comment`, passing the PR number as `issue_number` |

Three substantive additions beyond the tool swap:

1. **Owner/repo threading.** Every MCP call requires explicit `owner` and
   `repo`; the CLI inferred them from the checkout. The command now resolves
   them once from `git remote get-url origin` and passes them to every
   subagent.
2. **Commit SHA resolution.** Upstream warns not to write
   `$(git rev-parse HEAD)` into the comment body, because the body is rendered
   as Markdown and the command is never expanded — but it does not say where to
   get the SHA instead. The port names the source: `head.sha` from
   `pull_request_read` with `method: "get"`.
3. **Prior-PR search is capped** at the 3 most recent pull requests per
   modified file. The CLI path was one `gh` invocation; the MCP path is a
   commit lookup plus a search plus a comment read per candidate, which is
   unbounded on a file with long history.

Also changed: the attribution footer. Upstream ends its comment with
`🤖 Generated with [Claude Code](https://claude.ai/code)`. This environment
requires the standard footer form (a `---` rule, then
`_Generated by [Claude Code](https://claude.ai/code)_`) on every GitHub post, so
the two comment templates use that instead. The thumbs-up/thumbs-down feedback
line is unchanged.

Everything else — the five review lenses, the 0-100 confidence rubric quoted
verbatim to the scoring agents, the hard cut at 80, the re-check of eligibility
before posting, the false-positive list, and the permalink format rules — is
upstream's, unmodified.

## What it does

A fixed pipeline, not a freeform review:

1. Eligibility gate (Haiku): skip closed, draft, automated/trivial, or
   already-reviewed PRs
2. Collect CLAUDE.md paths (Haiku) — root plus every modified directory
3. Summarize the diff (Haiku)
4. Five parallel Sonnet reviewers, one lens each: CLAUDE.md compliance ·
   shallow bug scan · git blame and history · comments left on prior PRs
   touching these files · guidance in the code comments themselves
5. One Haiku scorer per finding, 0-100 confidence
6. Hard cut at 80 — below that is dropped, and if nothing survives it posts
   nothing
7. Re-run the eligibility gate
8. Post one conversation comment with SHA-pinned permalinks

## Relationship to the existing review skills

`.claude/skills/requesting-code-review/` and
`.claude/skills/receiving-code-review/` (from Superpowers) cover adjacent
ground but a different moment. Those are for review of work in progress in the
current session, before a PR exists. This command reviews a pull request that
is already open, from the outside, and writes its verdict to GitHub. They do
not conflict; nothing here supersedes them.

## Governance

This command posts publicly to a pull request. Two consequences:

- It is a write to an outward-facing surface. Confirm before running it against
  a PR in a repository that is not this one.
- Its output is only as good as the CLAUDE.md it audits against. This
  repository has no CLAUDE.md yet, which disables review lens 4a entirely and
  weakens the scoring rubric — the scorer is instructed to verify that a
  CLAUDE.md actually calls out any style issue, and with no file to check, such
  findings score low and are cut. Running `claude-md-improver` first is what
  makes this command's strongest lens work.
