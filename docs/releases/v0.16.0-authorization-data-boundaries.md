# Nehemiah Command v0.16.0 — Authorization and Data Boundaries

## Purpose

Prevent enterprise users and connected systems from crossing into Founder-private information while preserving the Founder’s authority across the complete operating system.

## Bounded domains

### Founder Private
Contains Founder decision memory, personal direction, capacity, standards, and private evidence. Only an authenticated Founder principal may read or write this domain.

### Enterprise
Contains MiP priorities, commitments, projects, owners, and operating status. Enterprise-shaped payloads are rejected when they contain protected private-context fields.

### Integration
Contains append-only inbound signals from approved systems. An integration principal may append only to the boundary matching its configured integration ID. Integrations cannot read Founder-private or enterprise data.

## Server enforcement

- `GET/PUT /api/founder-memory` requires a Founder session and Founder-private authorization.
- `GET/PUT /api/enterprise-context` requires a Founder session and enterprise authorization.
- `POST /api/integration-signals` requires matching integration ID/key headers and append authorization.
- `GET /api/integration-signals` requires a Founder session.
- Policy decisions are implemented in shared server-side authorization code rather than UI-only controls.

## Database changes

Run `docs/database/002-authorization-data-boundaries.sql` after the v0.14 Founder memory migration. It adds isolated enterprise context and integration signal tables.

## Configuration

`NEHEMIAH_INTEGRATION_KEYS` is a server-only JSON object mapping approved integration IDs to long random ingest keys.

## Security boundary

This release establishes application-level authorization and domain isolation. It does not yet replace integration keys with OAuth, provide enterprise user login, or complete security hardening, key rotation, and incident response.
